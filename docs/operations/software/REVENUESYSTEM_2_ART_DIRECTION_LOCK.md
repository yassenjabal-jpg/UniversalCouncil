# 0. Supersession law

This document **supersedes every previous RevenueSystem visual/art direction**.

From this date, RevenueSystem 2.0 has one visual authority only:

# EDITORIAL FINANCIAL ENGRAVING

Previous RevenueSystem directions, adaptations, candidate identities, palette interpretations, and design-language references are not active design authority.

Historical review/test documents may still mention earlier directions because they record what was tested at that time. Those references are **historical evidence only** and must never be used as visual authority for any RevenueSystem interface.

## Universal scope — no grandfathered UI

This lock applies to **every visible RevenueSystem surface without exception**:

- interfaces already implemented before this lock;
- RevenueSystem 2.0 workspaces already completed or functionally gate-passed;
- legacy screens that remain temporarily reachable;
- screens currently under rebuild;
- all future screens;
- windows, dialogs and popups;
- inspectors and side sheets;
- command palette and navigation chrome;
- login, lock, onboarding and database-selection states;
- report preview/print configuration surfaces;
- empty, loading, recovery, conflict, error and confirmation states;
- administration, diagnostics, backup/restore and system-health surfaces;
- every shared component and control template.

**No existing screen is grandfathered into an older visual direction.**

Functional/financial/test gates already passed remain valid as behavioral evidence, but they do **not** exempt those surfaces from visual migration. Every previously implemented RevenueSystem 2.0 surface must be visually rebased to Editorial Financial Engraving and pass the current Visual QA Gate before final release.

Legacy UI that will be retired does not need cosmetic preservation merely to extend its life; however, any legacy surface kept reachable in the release path must either:
1. be migrated to this visual system, or
2. be explicitly classified as a temporary compatibility surface with an approved retirement deadline.

This lock does not change the Media/YouTube Studio visual identity. It applies to all RevenueSystem UI only.

# 1. Origin of the final direction

The direction was derived from the eight generated RevenueSystem concept screens created on 2026-10-18:

1. Day Console / «اليوم»
2. Cashier Workbench / «حسابات الوارد»
3. Reconciliation Studio / «المطابقة»
4. Finance Ledger / «المالية»
5. Reports Center / «التقارير»
6. Data Operations / «البيانات»
7. Administration / «الإدارة»
8. Login / Lock

These images establish the **visual grammar**, not the literal data/content.

The Council and Studio explicitly distinguish between:
- **accepted visual language** from the images;
- **generation drift** that must not enter the product.

Accepted:
- engraved financial-paper materiality;
- deep-forest command rail;
- ivory operational field;
- cobalt interaction/focus;
- restrained institutional seals;
- guilloché/security-line structure;
- dense but calm data regions;
- clear Arabic financial hierarchy;
- document/ledger composition;
- compact Windows-desktop realism.

Rejected generation drift:
- Saudi national symbols/emblems;
- Saudi currency labels where the product data does not require them;
- architectural/bank-building imagery;
- palm/country imagery;
- literal banknote reproduction;
- real currency portraits;
- arbitrary country branding;
- left-side Windows controls when product rules require top-right controls;
- any fake operational values presented as product truth.

The concept images are visual references only. Repository/domain truth controls real labels, currencies, dates, calculations and workflow.

# 3. Design pillars

## 3.1 Precision first
Financial data is the hero. Art supports scanning, comparison, confidence and state recognition.

## 3.2 Institutional craft
Identity comes from the craft language of secure documents:
- engraved lines;
- guilloché;
- registration marks;
- ledger rules;
- seals;
- denomination strips;
- paper layering;
- precise alignment.

## 3.3 Quiet data, expressive shell
The closer a surface is to typing, arithmetic, tables or reconciliation, the quieter it becomes.

The closer a surface is to identity, context, status, empty space or report framing, the more artistic expression is allowed.

## 3.4 One dominant task
Every workspace must have one unmistakable operational focal region.

## 3.5 Desktop density without visual fatigue
Dense is allowed and often required.
Clutter is not.

## 3.6 Identity without imitation
The UI may recall banknote/security-print craftsmanship but must never imitate a real banknote, bank, government seal or national document.

`#2B73C9`

Use for:

## 4.5 Sky Blue
`#8EACD2`

Use for:

## 4.6 Warm Parchment
`#D9C8B1`

Target presence:
**5–10%**

Use for:
- paper layers;
- dividers;
- inactive document areas;

## 4.7 Brass Gold
`#B58A3E`

Target decorative presence:
**3–7% maximum**

Use only for:
- seal micro-detail;

`#151515`

- destructive action;
- serious error;

Red is never decorative.

## 4.10 Semantic Amber

Use for:

- recoverable issue.

# 5. Color weighting rule

Typical operational workspace:
- Paper Ivory: 50–60%
- Deep Forest: 12–20%
- Cobalt/Clear/Sky combined: 8–15%
- Warm Parchment: 5–10%
- Brass: 2–5%
- Semantic colors: only where state requires them.

Reports/Login may deviate modestly.
Data-entry and dense-grid screens must stay lighter and quieter.

# 6. Material language

## 6.1 Allowed materials

The application should visually evoke:
- warm financial paper;
- printed security linework;
- engraved ink;
- ledger sheets;
- institutional certificates;
- precise metallic annotation;
- document seals.

## 6.2 Surface hierarchy

### Surface A — Canvas
Paper Ivory, almost texture-free.

### Surface B — Work Paper
Ivory with extremely subtle warm grain.

### Surface C — Document Layer
Ivory/Parchment with hairline frame and small overlap.

### Surface D — Institutional Chrome
Deep Forest / Cobalt.

### Surface E — Verification
Deep Forest + restrained seal/detail.

## 6.3 Texture intensity

- data grid/input: **0–1% perceived texture**
- work panel: **1–2%**
- header/context band: **2–4%**
- seal/identity region: **4–8%**
- login/empty-state identity field: up to **8%**, never behind input text.

Patterns must disappear perceptually during active work.

## 6.4 Forbidden materials

No:
- glassmorphism;
- acrylic blur as identity;
- glossy gaming plastic;
- heavy drop shadows;
- fake leather;
- wood;
- marble;
- antique parchment;
- stained paper;
- steampunk metal;
- neon;
- holographic crypto effects.

# 7. Engraving vocabulary

The system uses four controlled pattern families.

## E1 — Guilloché Field
Thin looping security curves.

Use:
- header margins;
- shell identity areas;
- report cover/header;
- login background.

Never:
- behind tables;
- behind editable numbers.

## E2 — Registration Lines
Fine alignment/printing marks.

Use:
- process stepper;
- Data Operations;
- document mapping;
- reconciliation connectors.

## E3 — Ledger Rulework
Straight fine lines, double rules, sectional borders.

Use:
- tables;
- summary bands;
- section headers;
- report structures.

## E4 — Institutional Seal
Original RevenueSystem-specific abstract seal.

Use:
- verified/matched;
- day readiness;
- saved financial state;
- report certification;
- login identity.

Rules:
- no national emblems;
- no real bank seals;
- no coat-of-arms imitation;
- no currency portraits;
- one major seal maximum per workspace;
- secondary seals are micro-sized only.

# 12. Financial-number system

Money is a first-class visual object.

Every amount must communicate:
- value;
- currency;
- sign;
- source/context;
- state if relevant.

Rules:
- IQD coarse, IQD change, USD remain visibly separate;

# 13. Tables and dense data

Tables are not decorative objects.

## 13.1 Grid character
- clean Paper Ivory surface;
- hairline ledger rules;
- subtle alternating row tone only if needed;
- clear selected row via cobalt edge/band;
- right-aligned Arabic text by semantic rule;
- numeric columns aligned consistently;
- status icon + text, never color alone.

## 13.2 Header
- Warm Parchment or very light Forest/Blue tint;
- no full ornate pattern;
- stronger bottom ledger rule.

## 13.3 Row density
Designed for prolonged work.
Do not inflate row heights for visual fashion.

## 13.4 Error rows
Use:
- semantic red text/icon;
- pale red background;
- explicit reason.

# 19. Motion grammar

Motion exists to explain state, not decorate.

## 19.1 Timing
- focus/hover: 80–140 ms
- control state: 100–180 ms
- panel/inspector: 160–240 ms
- workspace transition: 180–300 ms

## 19.2 Allowed motion
- ledger/page shift;
- line-build for process flow;
- short focus trace;
- verification seal resolve;
- panel reveal;
- restrained denomination-strip transition.

## 19.3 Forbidden
- continuous pattern animation;
- spinning coins;
- animated money;
- glowing rails;
- parallax during entry;
- motion that steals focus or delays keyboard input.

# 26. Visual QA gate

Every RevenueSystem screen must pass:

1. Does it clearly belong to «المطابقة»?
2. Is the dominant task obvious within 2 seconds?
3. Is financial data easier to scan than the decorative layer?
4. Could a user work here for hours without visual fatigue?
5. Are IQD coarse/change/USD semantically separate where relevant?
6. Is focus visible?
