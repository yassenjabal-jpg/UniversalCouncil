# Agent Runtime Bake-off — Delay & Reliability Remediation Plan

Date: 2026-10-13
Scope: PR #25 / experiment/agent-runtime-bakeoff-20261013
Status: REVIEW COMPLETE — REMEDIATION REQUIRED BEFORE FINAL RUNTIME SELECTION

## Executive finding

Phase 1 mechanics produced useful evidence and the zero-cost Phase 2 infrastructure succeeded in producing live results, but the currently committed Phase 2 report is **not valid for final runtime selection**.

The primary reason is not one single model failure. The delay and stoppages came from three interacting classes of problems:

1. unstable YASSIN remote execution transport;
2. live harness and provider compatibility defects discovered only after long runs had started;
3. CI/evidence design that allowed stale or partial results to remain visible after later code fixes.

The current decision remains **NO_WINNER**.

### Why the current scores are not authoritative

The committed Microsoft results are 16/16 technical failures caused by:

`OpenAIChatCompletionClient.__init__() got an unexpected keyword argument 'timeout'`

Later commits attempted to correct MAF compatibility, and later GitHub Actions jobs show the MAF live job completing successfully. However those later runs did not produce a complete aggregate because other matrix jobs failed. Therefore the committed aggregate is from an earlier code state and does not represent the latest harness.

The baseline committed run contains 9 timeout failures out of 16 cases.

The OpenAI committed run contains 1 timeout failure out of 16 cases.

No final comparison is fair until all candidates are rerun from one identical tested SHA.

## Root cause inventory

### P0 — YASSIN / remote execution instability

Observed behavior:
- Desktop Commander commands timed out while checking/installing Ollama.
- even `ping` remained pending instead of returning promptly;
- YASSIN later became Offline;
- current device inventory shows YASSIN on Desktop Commander 0.2.52 while DESKTOP-RQUULE9 is Online on 0.3.0.

This version difference is a concrete remediation lead, not proof by itself that the old agent caused every timeout.

Impact:
- local GPU execution could not be completed;
- GUI/desktop evidence could not be collected;
- work moved to slower GitHub-hosted CPU runners;
- repeated transport retries consumed time without creating benchmark evidence.

### P0 — stale evidence lineage

The current committed Phase 2 results were generated by an earlier successful workflow run. Later fixes changed the live runner and MAF behavior, but the new runs did not replace the old aggregate.

Impact:
- repository head and benchmark evidence no longer describe the exact same executable state;
- a human reading only `report.json` could mistake stale diagnostics for current truth.

### P0 — Microsoft provider contract mismatch

The first committed MAF live result set failed all 16 cases because the runtime adapter passed an unsupported `timeout` constructor argument.

Impact:
- MAF score is meaningless for comparison;
- the workflow still produced a syntactically valid result file, which made a technical adapter failure look like a quality score.

### P0 — aggregate skipped when one matrix runtime fails

The live matrix is intentionally `fail-fast: false`, but the aggregate job uses normal `needs: live` behavior. When any matrix member fails, aggregation is skipped.

Impact:
- later corrected MAF/OpenAI evidence can exist as artifacts without a canonical consolidated report;
- stale aggregate files stay in the branch.

### P1 — long-run workflow triggered too early and too often

The heavy live workflow was triggered repeatedly while the harness was still changing.

Observed history includes multiple live runs for successive fixes.

Impact:
- expensive-in-time 16-case runs were used as interface discovery tests;
- small API mismatches were learned after model installation and case execution had already started.

### P1 — CPU runner + large call fan-out

Each case can require:
- routing;
- 2–7 independent role calls;
- synthesis.

Across 16 cases and 3 runtimes this creates hundreds of local-model calls.

On CPU-only hosted runners, this caused multiple 180-second request timeouts.

### P1 — baseline is not a faithful v0.3 control

The current live runner uses one common `run_case` orchestration shell for all runtimes. The baseline differs mainly in the model-call transport.

That means the live baseline receives routing/parallel-role/synthesis behavior from the new harness instead of faithfully representing the current v0.3 governance execution semantics.

Impact:
- baseline vs candidate comparison mixes architecture changes with transport/runtime changes.

### P1 — historical answer leakage

The model receives source artifacts that may contain the historical final decision or status.

Impact:
- exact decision correctness partly measures extraction/compliance with a known answer, not independent decision quality;
- OpenAI's current 93.75% correctness signal is encouraging but cannot by itself prove superior reasoning.

### P1 — misleading desktop metric

Non-desktop cases receive a desktop score of 1.0 automatically. The two desktop-required cases received no successful desktop execution, yet aggregate desktop score appears as 0.9.

Impact:
- the metric looks like “90% desktop success” even though actual required desktop-task completion is 0/2.

### P1 — live failure recovery measures harness behavior

The live runner's synthetic recovery path intentionally raises an exception before calling the model and then retries.

Impact:
- this measures harness recovery, not framework-native checkpoint/recovery semantics;
- native mechanics were tested separately in Phase 1 and should remain a separate metric.

### P2 — GUI access dependency

The requested architecture is GUI-primary / DC-secondary. In the current chat tool surface, direct screenshot/mouse/UIA actions were not exposed through Remote Desktop Commander. The YASSIN GUI bridge therefore still depends on a healthy command transport to invoke and collect evidence.

Impact:
- loss of DC also removes practical access to the local GUI bridge from this execution context.

## Remediation plan

### Gate 0 — freeze selection and invalidate stale selection evidence

Actions:
1. Keep PR #25 Draft.
2. Keep `main` unchanged.
3. Mark the current Phase 2 report as `DIAGNOSTIC_STALE_RUN — NOT FOR SELECTION`.
4. Preserve old results as evidence; do not delete them.
5. Require every future result set to record:
   - source/head SHA;
   - config SHA;
   - cases SHA;
   - model name and model digest;
   - framework package versions;
   - workflow/run ID;
   - runner type;
   - timestamp;
   - cost receipt.

Acceptance:
- evaluator refuses a result set whose provenance does not match the expected experiment manifest.

### Gate 1 — restore YASSIN execution reliability

Actions:
1. Update YASSIN Desktop Commander from 0.2.52 to the current approved 0.3.x release after reconnect.
2. Verify auto-start/reconnect after user login and reboot.
3. Add a lightweight health probe:
   - agent reachable;
   - shell round-trip;
   - repository readable;
   - GUI bridge reachable;
   - disk-space check;
   - GPU/NVIDIA check.
4. Store Ollama models on E: only.
5. Run Ollama locally only on `127.0.0.1`.
6. Verify the GUI bridge with one harmless application open/observe/close workflow and record before/after evidence.
7. Do not use DESKTOP-RQUULE9 or any other machine as a compute/recovery substitute. If YASSIN is unavailable, the live bake-off stops.

Acceptance:
- 10 consecutive health probes without timeout;
- one GUI semantic action round-trip with verified before/after receipt;
- local model probe returns cost_usd=0.

### Gate 2 — repair the benchmark architecture before rerun

Actions:
1. Create three explicit adapters:
   - `baseline_v03`: faithful current Council execution semantics;
   - `openai_agents`: OpenAI-native orchestration;
   - `maf`: Microsoft-native orchestration.
2. Keep prompts, source packet, model, seed, and grading identical.
3. Separate:
   - runtime reliability;
   - reasoning/decision quality;
   - governance compliance;
   - desktop execution.
4. Replace the average desktop score with a dedicated hard gate:
   - desktop-required cases passed / desktop-required cases total;
   - final eligibility requires 2/2.
5. Rename live synthetic recovery to `harness_recovery`.
6. Keep Phase 1 native checkpoint/HITL recovery as `runtime_native_recovery`.
7. Add a provider contract smoke test that instantiates each real adapter and completes one local call before any 16-case run.

Acceptance:
- one smoke case succeeds end-to-end for all three adapters;
- no unsupported-constructor/API errors;
- no candidate can enter the full run with an untested provider adapter.

### Gate 3 — remove historical answer leakage

Actions:
1. Build immutable case packets derived from source artifacts.
2. Remove/mask sections containing:
   - final verdict;
   - status;
   - explicit recommendation label;
   - later acceptance result.
3. Keep the expected answer in a separate grader-only file.
4. Record source artifact SHA and packet SHA.
5. Add at least four holdout cases where the answer cannot be copied from a visible status line.

Acceptance:
- model-facing packet contains no expected decision token;
- grader retains traceability back to original repository evidence.

### Gate 4 — YASSIN-local staged execution only

The live bake-off must not run on GitHub-hosted runners, DESKTOP-RQUULE9, or another computer.

Use the single entrypoint:

`tools/run_yassin_bakeoff.ps1`

Stages:
- `Preflight`: masked packets, unit tests, repository validation, Ollama-local check, and 10 consecutive YASSIN health probes;
- `Canary`: one case across all three runtimes;
- `Representative`: four cases only after a matching Canary receipt;
- `Full`: all 16 cases only after a matching Representative receipt;
- `Evaluate`: scoring only after the full manifest and desktop evidence are valid.

Rules:
- no automatic live run on Git push;
- no external compute fallback;
- results are written atomically after every case;
- completed cases resume only when the experiment provenance matches;
- incomplete stages never overwrite a valid completed-stage receipt.

Acceptance:
- Canary cannot run without YASSIN Preflight;
- Representative cannot run without a matching Canary receipt;
- Full cannot run without a matching Representative receipt;
- final scoring refuses non-Full manifests and stale provenance.

### Gate 5 — timeout and performance hardening

Actions:
1. Use YASSIN GPU as primary zero-cost live runner once healthy.
2. Do not use GitHub-hosted CPU execution or any other machine as fallback/cross-check for live decision runs.
3. Reduce model-facing source packet size after answer masking.
4. Apply explicit per-stage budgets instead of one generic 180-second timeout.
5. Retry only transient local-provider timeouts; do not retry schema/API defects.
6. Save one result immediately after every case so a late failure cannot discard earlier valid cases.
7. Resume from the last completed case instead of rerunning all 16.
8. Load the local model once and keep it warm across cases when running on YASSIN.

Acceptance:
- zero unexplained timeout failures in canary and 4-case gate;
- full run can resume without recomputing already-valid cases.

### Gate 6 — YASSIN desktop evidence

Run the desktop-required cases separately on the actual YASSIN execution plane:
- c02 GUI-primary hybrid;
- c04 After Effects runtime evidence.

Required evidence per case:
- before state;
- selected execution path;
- semantic selector/action receipt;
- screenshot or equivalent visual verification when available;
- after state;
- unintended-action check;
- recovery evidence if injected.

Acceptance:
- 2/2 desktop cases pass every required field;
- no coordinate-only fallback unless semantic control is unavailable and explicitly recorded.

### Gate 7 — final controlled rerun

Run order:
1. 1-case canary × 3 runtimes;
2. 4 representative cases × 3 runtimes;
3. all 16 cases × 3 runtimes;
4. YASSIN desktop 2/2 gate;
5. final evaluator.

Use one locked experiment manifest:
- same Qwen local model and digest;
- same seed;
- same masked case packets;
- same config;
- pinned framework versions;
- cost_usd = 0.

Final eligibility:
- all 16 cases completed for that runtime;
- zero adapter/runtime errors;
- zero policy violations;
- Phase 1 hard mechanics pass;
- desktop gate = 2/2;
- provenance manifest matches the evaluated SHA.

### Gate 8 — selection rule

Do not collapse all evidence into one opaque score.

Report four axes:
1. decision quality;
2. runtime reliability/recovery;
3. governance compliance;
4. latency/token efficiency.

If one runtime is materially better in quality and meets all hard gates, select it.

If quality is effectively tied, prefer:
1. fewer failures;
2. simpler integration;
3. lower latency/token burden;
4. easier observability and recovery.

Council v0.4 remains provisional until this gate passes.

## Current verdict

Useful work was completed, but the existing Phase 2 numbers must be treated as **diagnostic evidence, not a winner comparison**.

The largest process lesson is:

> Long live runs must never be used to discover basic adapter/API compatibility, and benchmark evidence must never outlive the exact code/config SHA that produced it.

The next valid milestone is not “run 16 cases again.” It is:

> pass transport health + adapter canary + provenance gate first, then run staged decision-quality evaluation, then finish with 2/2 YASSIN desktop evidence.
